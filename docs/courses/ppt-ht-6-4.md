## NEC：用清晰的语言管项目

<p class="dk-lead">英国土木工程师学会（ICE）颁布的新工程合同（NEC）系列，是国际上尤其在英国及英联邦国家广泛使用的代表性合同条件之一。</p>

- **三个特点**：语言清晰、选择灵活、管理理念前瞻，明显区别于传统合同模式。
- **核心文本**：工程施工合同（ECC），用于业主与总承包商之间的主合同，也用于总包管理的一揽子合同。
- **设计深度弹性**：ECC 同时包含工程设计和施工，承包商的工作可以是纯施工、施工加部分设计，也可以是设计施工 EPC。
- **模块化**：使用者可按需选择组合，核心条款必选，次要选项条款可选。

<template #notes>

NEC 和 FIDIC 的最大区别不在条款内容，而在「写法」：NEC 用短句、常用词，把规则写得像操作手册。ECC 又是 NEC 系列的基础文本，所以这一节的重心是 ECC 的模块结构和合作机制，而不是逐条背条款。

</template>

</Slide>

## 核心条款：九条撑起基本构架

<span class="dk-tag">总则</span><span class="dk-tag">承包商的主要责任</span><span class="dk-tag">工期</span><span class="dk-tag">测试和缺陷</span><span class="dk-tag">付款</span><span class="dk-tag">补偿事件</span><span class="dk-tag">所有权</span><span class="dk-tag">风险和保险</span><span class="dk-tag">争端和合同终止</span>

- 核心条款是施工合同的**主要共性条款**，共 **9 条**。
- 它构成施工合同的基本构架，适用于施工承包、设计施工总承包和交钥匙工程承包等不同模式。
- 九条之中，「补偿事件」是 ECC 最具特色的制度，后面单独展开。

<Reveal label="核心条款和主要选项条款是什么关系？">

核心条款是**必选**的共性规则；主要选项条款是对核心条款的**补充和细化**，使用者根据项目需要，在六种计价模式中选择**一个且只能选择一个**，纳入合同条款之中。

</Reveal>

<template #notes>

九条不用逐字背，但要知道「补偿事件」在核心条款里，而不是次要选项。核心条款管共性，主要选项管计价，这个分层是 ECC 模块化的关键。考试常问「主要选项能选几个」，答案是一个。

</template>

</Slide>

## 次要选项、成本组成表与合同数据

- **次要选项条款**：十多项可选，包括履约保证、母公司担保、支付承包商预付款、多种货币、区段竣工、承包商对其设计只承担合理技术与精心设计责任、通货膨胀价格调整、保留金、提前竣工奖金、工期延误赔偿费、功能欠佳赔偿费、法律变化等。
- **成本组成表**：对成本组成项目的全面定义，分成本组成表和成本组成简表，分别与不同计价方式关联；业主按具体项目选择，并删除与本合同无关的列项。
- **合同数据**：对条款补充信息的约定，使用者可自由定义。例如 ECC 合同范本适用于不同设计深度，承包商承担的设计职责可在合同数据中约定。

<Reveal label="一份完整的 ECC 合同是怎么组合出来的？">

在**核心条款**的基础上，加上选定的**主要选项条款**和**次要选项条款**，就可以组合形成一个内容约定完备的合同文件。成本组成表和合同数据则按计价方式和项目需要配套填写。

</Reveal>

<template #notes>

这一页是「配件清单」：次要选项决定加哪些特殊安排，成本组成表决定钱怎么算，合同数据决定项目-specific 的信息填什么。组合公式要记住：核心 + 主要选项 + 次要选项。成本组成表分「表」和「简表」，分别对应不同计价方式，不能混用。

</template>

</Slide>

## 合作伙伴管理：ECC 的底层价值观

<p class="dk-lead">鼓励当事人采取合作，而不是对抗，是 ECC 合同的典型特点。核心条款总则第一条就提出业主、承包商、项目经理和工程师相互信任、相互合作。</p>

<CompareCard title="ECC 合作机制的三大支柱" :cols="['合作伙伴', '早期警告', '补偿事件']" :rows="[

  { k: '与传统合同的区别', v: ['以共同愿景减少冲突、降低风险', '把事后索赔前置为事前预警', '替代传统索赔条款实现的功能'] }

这三根支柱是一条链：合作伙伴提供组织基础，早期警告提供发现机制，补偿事件提供救济机制。教材有一句总结很重要——传统施工合同中由索赔条款实现的功能，在 ECC 中由早期警告和补偿事件两项程序优化并解决。

## 早期警告：问题还没变大就说出来

<Steps title="早期警告的程序" :steps="[
  { t: '发出警告', d: '一经察觉发现可能出现增加合同价款、拖延竣工、工程使用功能降低等问题，项目经理或承包商均应向对方发出早期警告' },
  { t: '要求开会', d: '项目经理和承包商都可要求对方出席早期警告会议；每一方都可在对方同意后要求其他人员出席' },
  { t: '会议合作', d: '提出并研究建议措施以避免或减少影响；寻求对受影响各方均有利的解决办法；决定各方应采取的行动及依合同应采取行动的一方' }
]" />

- 项目经理应在早期警告会议上把研究的建议和作出的决定**记录在案**，并将记录发给承包商。
- 其他体现：承包商应在获得和提供工程信息方面与其他方合作；发现合同文件存在歧义和矛盾，项目经理或承包商均应**立即通知**对方，由项目经理发出指令解决；发现工程信息有不合法、不可行的要求，承包商应立即通知项目经理，项目经理同意后发出指令适当变更。

<template #notes>

早期警告的精髓是「一经察觉」而不是「确认之后」，把预警时点尽量前移。会议的三项合作任务要能复述，记录责任在项目经理。教材还把它延伸到信息合作、歧义处理和不可行要求，说明这不是一个孤立程序，而是贯穿合同的管理习惯。

</template>

</Slide>

## 补偿事件：不是索赔，但解决索赔的问题

<p class="dk-lead">补偿事件是指一些非承包商过失原因引起的事件，承包商有权根据事件对合同价款及工期的影响要求补偿，包括额外付款和工期延长。</p>

- **典型情形一**：承包商遇到现场内非气象条件引起的、有经验的承包商在合同生效日判断出现概率极小因而有理由不予考虑的实际条件。
- **典型情形二**：一个日历月内，合同竣工日前合同资料指明场所记录的气象实测资料，与气象资料相比，该值平均出现频率低于**十年一遇**。
- **谁可以通知**：项目双方均可通知补偿事件，鼓励各方及早告知，减小事件的不利影响；通过项目经理通知，体现业主就补偿事件给予补偿的**主动性**。

<Reveal label="补偿事件的影响一时算不清，怎么办？">

若项目经理作出决定，认为某一补偿事件的影响**过于不明确以致无法合理预测**，此时应在向承包商发出提交报价的指令中说明其关于补偿事件的**假定条件**，先以此假定条件为基础计价；事后若发现假定有误，项目经理应通知改正。

</Reveal>

<template #notes>

补偿事件和索赔的功能相似，但发起主体不同：ECC 允许业主方主动通知，把「承包商追着要钱」变成「双方一起算账」。两个例子要记关键词：非气象条件的实际条件、气象数据低于十年一遇。影响算不清时先作假定、快速处理，事后有误再改，这是 ECC 追求效率的体现。

</template>

</Slide>

## 补偿事件的计价：信息是谁提供的，就对谁不利

<CompareCard title="变更工程信息引发补偿事件的计价原则" :cols="['计价原则']" :rows="[
  { k: '变更由业主提供的工程信息', v: ['该补偿事件的影响按对承包商最有利的解释进行计价'] },
  { k: '变更由承包商提供的工程信息', v: ['按对业主最有利的解释计价'] },
  { k: '制度目的', v: ['鼓励双方相互提供真实可靠的工程信息，而不是提供对己方最有利的信息'] }
]" />

> 这条规则看似「偏心」，实则是**激励相容**：谁提供的信息，谁就要为信息的质量负责。

<template #notes>

这条计价原则是 ECC 合作理念最精妙的地方：业主提供的信息有歧义，按对承包商最有利的解释算；承包商提供的信息有歧义，按对业主最有利的解释算。结果是双方都不敢在信息里「留一手」，从制度上逼出真实信息。

</template>

</Slide>

## 小结：ECC 的三层结构

<p class="dk-lead">模块是形，合作是魂，补偿事件是把索赔变成共同算账。</p>

- **结构**：核心条款 **9 条**必选；主要选项 **6 选 1**；争议程序 **3 选 1**；次要选项、成本组成表、合同数据按需配置。
- **计价**：标价合同、目标合同、成本补偿合同、管理合同，按范围确定程度和开工急迫程度选择。
- **合作**：合作伙伴（发起人 + 核心小组）、早期警告（一经察觉即通知）、补偿事件（双方均可通知）。
- **计价原则**：业主提供的信息按对承包商最有利解释，承包商提供的信息按对业主最有利解释。
